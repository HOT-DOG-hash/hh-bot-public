# P2.1 Ranking Spike — Data & Procedures

## 1. Цели
- Подготовить обезличенные датасеты для оффлайн/онлайн оценки новых моделей ранжирования.
- Задокументировать pipeline анонимизации и проверки качества.

## 2. Datasets (raw → cleaned → features)

### 2.1 Raw слои
| Набор | Схема | Формат | Размерность (30 дней) | Примечания |
| --- | --- | --- | --- | --- |
| `vacancies_YYYYMMDD.jsonl` | см. `SAMPLE_SCHEMA.md#vacancies` | JSONL | ≈ 120 000 вакансий | включает текст описания, salary, сегменты |
| `responses_YYYYMMDD.jsonl` | `SAMPLE_SCHEMA.md#responses` | JSONL | ≈ 1.5 млн строк | отклики пользователей, содержит outcome |
| `clicks_YYYYMMDD.parquet` | `SAMPLE_SCHEMA.md#clicks` | Parquet | ≈ 8 млн событий | клики/показы (ranking logs) |

### 2.2 Cleaned слои
| Файл | Описание | Поля (ключевые) | Размер |
| --- | --- | --- | --- |
| `vacancies_clean.parquet` | обезличенные вакансии | vacancy_id, industry, skills[], emb_vec | ≈ 80 MB |
| `interactions.parquet` | пользователь-вакансия взаимодействия | owner_id_hashed, vacancy_id, label_int | ≈ 250 MB |
| `labels.parquet` | аггрегированные метки релевантности | vacancy_id, relevance_score | ≈ 12 MB |

### 2.3 Features
| Каталог | Содержимое | Использование |
| --- | --- | --- |
| `bm25_index/` | сериализованный BM25 словарь и postings | baseline scoring |
| `tfidf_vectors/` | TF-IDF матрицы (sparse) | baseline + feature stacking |
| `cooccurrence/` | матрицы совместных просмотров | candidate features |

## 3. Pipeline анонимизации
1. Загрузить актуальные сырые файлы в `raw/`.
2. Выполнить анонимизацию:
   - поля `email/phone/user_id` → `hash_sha256(value + salt)` (соль из Vault).
   - временные отметки округлить до часа.
   - свободный текст пропустить через NER-маску (удалить PII, оставить business context).
3. Сохранить результаты в `cleaned/` (`vacancies_clean.parquet`, `interactions.parquet`, `labels.parquet`).
4. Сформировать признаки в `features/` (BM25 индекс, TF-IDF векторы).
5. Сохранить лог выполнения в `research/datasets/quality_logs/`.

## 4. Проверка качества
- Проверка заполненности обязательных колонок (≥95%).
- Поиск дубликатов (ключ `owner_id + vacancy_id`); результат <1% за 7 дней.
- Проверка согласованности временных диапазонов (не выходят за окно 30 дней).
- Отчёт о проверках приложить в `quality_logs/`.

## 5. Privacy & Legal
- **PII удаляется/хэшируется**: email, phone, фамилии → `SHA-256(salt+value)`, соль хранится в Vault (доступ только у ML/SRE lead).
- **Free-text**: маскирование имен и контактов через NER (spaCy ru) + словари стоп-слов, результат логируется.
- **Timestamp handling**: округление до часа, timezone → UTC.
- **Retention**:
  - Raw: 60 дней (архив в S3, доступ только Data Platform).
  - Cleaned: 180 дней (используется спайком и регрессиями).
  - Features: 90 дней (перегенерация при каждой новой выборке).
- **Доступы**:
  - `research/datasets/raw` — группа `data-engineering` (read), `ml-team` (read, по запросу).
  - `research/datasets/cleaned` — `ml-team` (read/write), `analytics` (read).
  - `research/datasets/features` — `ml-team` (read/write).
- **Проверка необратимости**: ежеквартально генерировать 1 000 случайных хэшей и проверять отсутствие пересечений с известными PII (скрипт `privacy_check.py`, TODO).

## 6. Offline Metrics
- **Labeling** (source: `research/datasets/cleaned/labels.parquet`):
  - label = 2 ⇒ пользователь подал отклик и получил позитивный итог (accept/meeting).
  - label = 1 ⇒ был клик/ответ без accept.
  - label = 0 ⇒ показ без взаимодействий.
- **Метрики** (per query / owner session):
  - `Precision@K = |relevant@K| / K`.
  - `nDCG@K = DCG@K / IDCG@K`, где `DCG@K = Σ (2^{label_i} - 1) / log2(i+1)`.
  - `MAP@100 = mean(average_precision)` на топ-100 позиций.
- **Baseline**: текущая продовая выдача BM25 + TF-IDF с правилами (boost свежих вакансий, фильтр opt-out).
- **Кандидаты**: ML-модели (градиентный бустинг, нейросеть) — пока только документация, без реализации.
- **Окно данных**: baseline берёт 30-дневный срез (`baseline_YYYYMMDD`, см. README); train/val делятся 20/7 дней, test — последние 3 дня. Разметка замораживается по UTC.
- **Минимальный размер выборки**: ≥5k сессий owner_id на fold, иначе объединяем соседние недели (логика описана в `offline_eval/README.md`).
- **Агрегация**: baseline и каждый кандидат обязаны публиковать `metrics_summary.csv` + `metrics_by_segment.csv`; CI 95% хранится в `bootstrap_stats.json`.

## 7. Protocol
- **Splits**:
  - Holdout: последний календарный месяц → тест, предыдущие два → train/val.
  - Time-based k-fold (K=4): каждая неделя = fold, окно скользит (train weeks 1..k-1, test = week k).
  - Для экспериментов с недостатком данных допускается stratified sampling по плану (`plan_code`).
- **Агрегация и статистика**:
  - Метрики считаются по каждому fold/holdout.
  - Bootstrap по `owner_id` (1 000 выборок) → mean, std, 95% CI (percentile метод).
  - Для MAP/Precision — проверка на устойчивость (порог SE < 0.01).
- **Визуализации**:
  - Line plot Precision@K и nDCG@K (baseline vs candidate).
  - Gain chart (кривая накопленной релевантности).
  - Boxplot распределения метрик по folds.
- **Отчётная таблица**:
  - `metrics_summary.csv`: колонки `model`, `split`, `metric`, `value`, `ci_low`, `ci_high`.
  - `metrics_by_segment.csv`: сегменты по плану (`plan_code`), гео.
  - Все артефакты в `research/offline_eval/experiments/<exp>/`.

## 9. Online Metrics & Experimentation
- **Основная метрика**: Accept Rate (accepts / delivered) на 7-дневном окне; агрегируется по owner_id.
- **Secondary**: CTR (clicks/impressions), response rate, время до отклика.
- **Лаг**: события собираются в ClickHouse, лаг ≤ 15 минут; мониторинг `webhook_lag_seconds`.
- **Guard Rails**: opt-out spike, платежи (failed), scheduler lag.
- **Фичефлаг**: `ENABLE_ML_RANKING` (см. `backend/app/feature_flags.py`) — boolean, контролирует включение ML-ранжирования для сегментов.
- **Стратификация**: по тарифному плану (`plan_code`), географии, каналу доставки.
- **Экспозиция**: 50/50 (control vs treatment), с возможностью ramp-up (10% → 50%).
- **Risk Limits**: если Accept Rate падает >5 p.p. либо CTR < baseline, эксперимент приостанавливается.
- **Логирование**: события impressions/clicks/accepts маркеруются `experiment_id`, `variant`, `timestamp_hour`. Контроль и treatment пишут в одну таблицу с колонкой `enabled_ml`.
- **Мониторинг**: CTR/Accept Rate графы размещены в `docs/dashboards/grafana/growth_billing.json`; алерты (`NotificationLatencyHigh`, `OptOutSpike`) подключены для автоматического rollback.
- **Решение по ramp-up**: шаги 10% → 50% → 100% по 24 часа, при соблюдении guard rails. Каждое расширение требует review записи в RUN_LOG.

## 10. Decision Framework
- **Go**: Accept Rate ≥ +2 p.p. vs control (p-value < 0.05) и CTR ≥ baseline; guard rails в норме.
- **No-Go**: Accept Rate ↓ ≥ 3 p.p. или любой guard rail срабатывает > 2 часов; latency > SLA (60с p95).
- **Continue**: результаты незначимы, требуется дополнительный сбор данных.
- **Risks**:
  - Data shift (новые вакансии без историй) → запуск холодного старта.
  - Latency degradation → мониторинг `delivery_notification_latency_seconds`.
  - Ethical: убедиться, что ML не снижает видимость вакансий с льготами.
- **Follow-up**: подготовить финальный отчёт (см. `ml_ranking_report_TEMPLATE.md`), оформить lessons learned, обновить backlog для P2.2.
- **Rollout критерии**:
  - `Go`: включить `ENABLE_ML_RANKING` для 100% трафика, добавить постоянный мониторинг CTR/Accept Rate, запланировать переобучение каждые 4 недели.
  - `No-Go`: откатить фичефлаг, создать remediation ticket с описанием провала (данные/модель/инфраструктура).
  - `Continue`: определить дополнительный объём данных (дней, сессий) и дату повторного замера.
- **Документирование**: финальный отчёт рассылается Stakeholders (Product, Ops, Finance) и хранится в Git (`reports/ml_ranking/<exp>/`).
